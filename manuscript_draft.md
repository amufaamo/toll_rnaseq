# MultiverseDEG: multiverse differential expression analysis with calibrated stability in a graphical interface

## Abstract
**Background:** Differential expression (DE) analysis of bulk RNA-seq requires a series of defensible but arbitrary choices — low-count filtering, normalisation, model family, shrinkage, and nuisance-covariate adjustment. Each combination is a valid pipeline, and the resulting gene list depends on which one the analyst happened to select. Existing graphical interfaces for RNA-seq make one such pipeline easy to execute and, in the case of iDEP, easy to reproduce, but they leave the dependence of the result on that selection invisible.

**Results:** We present MultiverseDEG v4.0, an R/Shiny application for analysis from a count matrix to journal-ready figures, whose central component is a multiverse DEG module. Instead of running a single pipeline, the module enumerates the legal combinations of analytic choices for one biological contrast (80 in the full design; an 8-path subset in the current implementation), runs all of them, and ranks genes by *stability* — the fraction of specifications in which a gene is called, with a required 0.90 direction-consistency. Stability is calibrated against a parametric negative-binomial bootstrap null constructed from the full fitted model with the condition coefficient set to zero, yielding an effective FDR (eFDR) curve over stability thresholds. On a synthetic benchmark (400 genes, 40 true DE genes, n = 6 per group, B = 10), the eFDR curve was monotone non-increasing in the stability threshold, and the automatically selected threshold τ = 0.125 returned 33 calls with zero false discoveries (realised false discovery proportion 0.000 against a 0.10 target), recovering 33 of the 40 true DE genes. On three public datasets (`airway`, `pasilla` and GSE60450; four contrasts, B = 20), the curve was likewise monotone, the stability ranking placed known marker genes at the top, and complete calibrated runs took 8–27 minutes; in every run, however, the eFDR already met the target at the smallest attainable threshold, so the automatic rule selected it and the single default pipeline's DEG list was a strict subset of the multiverse calls. Results are presented as a stability-ranked table and a per-gene specification curve, and are passed to the downstream enrichment modules under an explicit `multiverse_stability` result type.

**Conclusion:** MultiverseDEG makes the analytic multiverse of a bulk RNA-seq contrast explicit and computable from a graphical interface, and reports a calibrated error rate for the stability criterion rather than a single pipeline's *p*-values.

**Availability:** Source at https://github.com/amufaamo/toll_rnaseq; container image `ghcr.io/amufaamo/easy-rna-seq:dev`.

## Introduction
RNA sequencing is routine in biological and clinical research, and a large part of its analysis is now well standardised: quality control, quantification, normalisation, differential expression, and functional enrichment. What is not standardised is the specific configuration of those steps. A gene is declared differentially expressed only after the analyst has chosen a low-count filter, a normalisation, a model family and test, whether to shrink log fold-changes, and whether to adjust for a measured covariate. Every one of these choices is defensible; none is uniquely correct.

This is the problem of researcher degrees of freedom. Steegen et al. [12] proposed reporting the *multiverse* of datasets and analyses consistent with the stated design rather than a single path through it, and Simonsohn, Simmons and Nelson [13] formalised specification curve analysis, in which the effect of interest is plotted across all reasonable specifications together with the choices that generated each one. In biomedical data analysis the same phenomenon has been quantified as vibration of effects, where the estimated association for a fixed exposure–outcome pair shifts materially across defensible model specifications [14]. Bulk RNA-seq DE analysis has exactly this structure, and the number of legal specifications is not small: filtering, normalisation, model family, shrinkage and covariate adjustment generate 80 legal combinations under conservative defaults.

Graphical interfaces have made RNA-seq analysis accessible to researchers without command-line experience. Galaxy [1] provides a broad tool collection on shared or cloud infrastructure; iDEP [2] and DEBrowser [3] provide capable downstream analysis starting from a count matrix. Importantly, reproducibility of the selected workflow is not an open problem in this class of software: iDEP already records the selected parameters and emits R/R Markdown code for the analysis that was run [2]. The gap is different. These tools, including the reproducible ones, faithfully document *one* path and say nothing about the other paths that were equally available. A perfectly reproducible analysis can still be a fragile one.

MultiverseDEG v4.0 addresses that gap. Its multiverse DEG module fixes one biological contrast, enumerates the legal analytic specifications, runs all of them, and ranks genes by how consistently they are called across the multiverse rather than by a single pipeline's adjusted *p*-value. Because a stability threshold is not itself an error rate, the module calibrates stability against a dataset-specific parametric null generated by negative-binomial simulation from the fitted model with the condition effect removed, and reports an effective FDR for each stability threshold. The output is not a diagnostic warning but a usable product: a ranked gene list with an attached error-rate estimate, a per-gene specification curve, and a hand-off into the existing enrichment modules.

The remainder of the article describes the software architecture and the multiverse engine (Implementation), reports the synthetic-data calibration, validation on three public datasets, and measured computational cost (Results and Discussion), and states what the current implementation does not yet establish (Limitations).

## Implementation

### Scope
MultiverseDEG v4.0 operates on a gene-by-sample matrix of integer counts plus a sample metadata table. Alignment and quantification of raw reads (FASTQ to counts) are outside the scope of the v4 package; earlier, separately maintained versions of this project contained a Nextflow-based upstream pipeline, but that code is not part of the application described here and is not distributed with it. Integrating an upstream pipeline into v4 is planned but not implemented, and no end-to-end claim is made.

### Architecture overview
The application is a `golem`-packaged Shiny application [6] with a `bslib` v5 user interface [7]. Application state is held in an R6 `AppState` object that carries the uploaded data, per-module results, a step-status map, and a parameter log shared across modules. The package and its dependencies are distributed as a Docker image, which launches the v4 package directly; all computation runs locally or on a user-controlled server, so count matrices and metadata need not be uploaded to a third-party host.

### Analysis modules
The interface is organised as ten sequential steps: (1) Upload of counts and metadata with format validation; (2) QC and filtering by expression thresholds; (3) exploratory data analysis, including PCA and sample clustering; (4) differential expression using `DESeq2` [4] with optional `apeglm` shrinkage [8] or `edgeR` [15]; (5) multiverse DEG analysis, described below; (6) over-representation analysis with `clusterProfiler` [9]; (7) gene set variation analysis; (8) UpSet comparison of DEG sets from different biological contrasts; (9) time-series analysis via `maSigPro` [10]; and (10) report generation. A journal-ready export dialogue is reachable from the plotting modules. Steps 4, 5, 6, 7 and 9 run their computations asynchronously.

### Multiverse DEG analysis

**Specification grid.** The engine starts from raw integer counts rather than a pre-filtered matrix, because filtering is one of the varied dimensions. For a single contrast it crosses two low-count filters (count ≥ 10 in at least as many samples as the smaller group; `edgeR::filterByExpr` using the design matrix) with four method arms: DESeq2 Wald without shrinkage, DESeq2 Wald with `apeglm` shrinkage, edgeR quasi-likelihood F-test with TMM normalisation, and edgeR likelihood-ratio test with TMM normalisation. This yields eight specifications, doubling to sixteen when the user nominates a metadata covariate, which adds a condition-plus-covariate design alongside the condition-only design. The full design described in the accompanying design document extends this to 80 legal specifications by adding DESeq2 LRT, edgeR RLE and upper-quartile normalisation, and limma-voom.

The grid is a product over family-legal choices, not a Cartesian product over all options. Normalisation factors are never crossed between families — edgeR TMM/RLE/upper-quartile factors are never passed alongside DESeq2 size factors — and `apeglm` shrinkage is applied only to a uniquely identified DESeq2 Wald coefficient. Specifications whose design matrix is rank-deficient, whose covariate is confounded with the condition, or whose filter leaves too few genes are pruned before computation, with the reason recorded. Filters are re-applied within every specification and within every bootstrap replicate; filter masks and normalisation factors are never reused across specifications.

**Stability.** For a call rule consisting of an adjusted-*p* cutoff *q* and an absolute log2 fold-change cutoff *a*, each gene receives an up-indicator and a down-indicator per specification. Directional stabilities are the means of those indicators over the *m* specifications, and the gene's stability *T* is their maximum. Direction consistency *C* is the ratio of *T* to the sum of the two directional stabilities: a gene called up in half the specifications and down in the other half has *T* = 0.5 and *C* = 0.5, and is not treated as stable. A call requires *T* ≥ τ and *C* ≥ 0.90. Genes removed by a filter, untested, or arising from a failed fit contribute zero indicators while remaining in the denominator, which is conservative for low-expression genes. Specifications are weighted equally because the declared grid, not an assumption of independence between paths, is the target of the summary; the module reports how many specifications belong to each method family so that an unbalanced grid is visible.

Call thresholds are deliberately not axes of the grid. Every fit stores the log2 fold-change, raw *p*-value and BH-adjusted *p*-value, so changing *q*, *a* or τ re-thresholds stored statistics without refitting any model.

**Calibrated effective FDR.** A stability threshold is not an error rate, so the module calibrates it by simulation. The full negative-binomial model (condition, plus covariate when specified) is fitted with DESeq2 to obtain size factors and trended/MAP dispersions. The null mean is then constructed from that same fit by setting only the condition coefficient to zero while retaining the intercept, covariate coefficients and count-scale normalisation factors. Fitting the null model *without* the condition term instead would absorb true condition effects into the dispersion estimates, inflate dispersions for genuinely differential genes, and bias the expected number of null discoveries downward; the resulting eFDR would be anti-conservative. To protect this construction against silent breakage by a future DESeq2 version, the engine reconstructs the full fitted mean from the coefficients and asserts equality with DESeq2's own `mu` assay to floating-point tolerance before zeroing the condition coefficient, and refuses to simulate otherwise.

For each of *B* replicates the engine simulates integer counts from the negative-binomial null, preserving sample order, metadata, covariates and condition labels, and reruns every filter and every specification from scratch to obtain a null discovery count *R_b*(τ). With the observed count *R*obs(τ), the reported curve is

eFDR(τ) = min{1, [(1 + Σ_b *R_b*(τ)) / (B + 1)] / max{*R*obs(τ), 1}},

which is undefined where no calls are made. The curve is evaluated at every attainable stability value *k/m*. Because a gene of stability *T* is called at every threshold τ ≤ *T*, its eFDR is the minimum of the raw curve over τ ≤ *T*; the raw values are therefore made monotone by a cumulative minimum taken in **ascending** τ. This is the mirror image of the sweep direction used in *p*-value-based q-value construction, since stability runs in the opposite direction to a *p*-value. Each gene receives the monotone eFDR evaluated at its own stability, which preserves the stability ranking; τ = 0 is excluded from automatic selection because it imposes no cross-specification support. The module then selects the smallest positive τ meeting the user's eFDR target. Only bootstrap discovery counts are retained; per-gene bootstrap arrays are discarded. B = 20 is permitted only as an exploratory setting and refuses targets below 0.10; B = 100 is the default.

**Outputs and hand-off.** Results are shown as a stability-ranked table and a per-gene specification curve. In the curve, each column is one specification, ordered by that gene's log2 fold-change; the upper panel plots signed −log10(adjusted *p*), positive for up and negative for down, which places DESeq2 and edgeR on a common test-strength scale despite their non-comparable standard errors, and the lower matrix shows the filter, normalisation, method, shrinkage and covariate of each column. Colours are Okabe-Ito, and every colour-coded category is also labelled, so colour is never the only encoding. The plot is built from a single long data frame with a shared specification rank and `facet_grid`, using `ggplot2` alone.

On selection, one data frame is added to the shared results list under the key `multiverse:<test>_vs_<reference>`, which cannot be mistaken for a biological contrast. Its `log2FoldChange` is the median log2 fold-change over tested specifications agreeing with the gene's direction, `stat` is signed stability, `padj` is the gene's monotone eFDR, and `pvalue` is `NA` because no valid pooled raw *p*-value exists. The table carries a `multiverse_stability` result-type attribute so that downstream consumers, which otherwise interpret `padj` as a per-gene BH q-value, can display the distinction; the enrichment modules read gene, `padj` and absolute log2 fold-change, and the fallback path must not attempt to use the all-`NA` *p*-value column. Contrast, specification count, bootstrap *B*, seed, target eFDR and selected τ are written to the session parameter log.

**Scheduling and cost.** The work is approximately (*B* + 1) × |*S*| model fits plus the null fit and simulation. Rather than one opaque long-running promise, the module submits bounded batches through `ExtendedTask` with `promises`/`future`: a batch returns plain arrays and counts, the main session merges them, updates a progress record, and queues the next batch. Worker processes never touch reactive APIs, and the module honours the application-wide `future` plan rather than setting its own, so it does not contend with the other asynchronous modules. Re-thresholding (changing τ, *q* or *a*, re-sorting, or selecting a different gene) triggers no refitting; changing a filter, method, covariate, *B* or seed starts a new run.

### Asynchronous computation
DESeq2 fits, GSEA permutations, the multiverse grid and the bootstrap are executed in background R processes via the `ExtendedTask` API with `future` and `promises`, so the interface stays responsive and can report progress. This uses the standard Shiny asynchronous interface available since Shiny 1.8.1 and is not itself novel; for the multiverse module it is a practical requirement rather than a convenience, because a calibrated run is hundreds of model fits rather than one.

### Journal-ready export
Figures can be exported through a dialogue offering page-width presets for *Nature* (89 mm single-column, 183 mm double-column), *Cell* (85 mm, 174 mm) and *Science* (57 mm, 122 mm), with a settable base font size, using the `cairo_pdf` device so that system fonts are embedded in the output and text renders identically across viewers. SVG export is also provided for subsequent editing in vector graphics software. This removes a repetitive manual step in figure preparation; we present it as a practical convenience, not as a scientific contribution.

### Colorblind-safe defaults
Discrete categories use the Okabe-Ito palette and continuous scales use `viridis` by default, following the recommendation of Wong [11], and categorical encodings in the specification curve are additionally labelled so that colour is never load-bearing on its own.

### Reproducible script generation
The application records analysis parameters as the user works and can emit a commented R script for the session. This is useful but not new: iDEP provides comparable code generation [2]. We report it as an implemented feature and make no priority claim for it.

## Results and Discussion

### Calibration on synthetic data
We evaluated the calibration of the stability/eFDR procedure end to end on a simulated dataset of 400 genes with 40 true differentially expressed genes and n = 6 per group, using the 8-path grid with B = 10 bootstrap replicates. This run is fully reproducible from a fixed seed (`scripts/generate_fig3_specification_curve.R`, using the fixture in `tests/testthat/helper-multiverse.R`). The eFDR curve was monotone non-increasing in τ and took two distinct values across the attainable thresholds, and the monotonisation step was idempotent when re-applied to the corrected curve. The automatically selected threshold was τ = 0.125 — the smallest attainable positive stability on an eight-specification grid — at which the procedure returned 33 calls with zero false discoveries (realised false discovery proportion 0.000), comfortably meeting the 0.10 target, and recovered 33 of the 40 true differentially expressed genes. This single synthetic realisation should not be read as a general guarantee of zero false discoveries: the effect size in this fixture (|log2FC| = 1.5) is large relative to the call rule's |log2FC| ≥ 1 threshold, and the eFDR bound is expected, not exact, in any one run.

The supporting unit and integration test suite comprises 68 tests: engine-level tests covering specification pruning, hand-calculated stability and eFDR arithmetic, determinism under a fixed seed, the state hand-off contract and a known-truth calibration check, plus `shiny::testServer()` integration tests exercising the module's actual reactive wiring (`shinytest2`/a headless browser were unavailable in the verified environment). All 68 pass with the slow statistical tests enabled.

We note one instructive negative result from development. An early implementation applied the monotonisation sweep in the wrong direction, which collapsed the eFDR curve and effectively disabled the stability threshold. The full test suite, including the known-truth FDR check, passed with that defect present, because the simulated effects in the test fixture (log2 fold-change 1.5 at n = 6 per group) were strong enough that even an unselective rule stayed inside the tolerance. The defect was found by reading the estimator, not by running the tests. Calibration checks for this class of estimator therefore need fixtures with weak effects, and a passing test suite should not be read as evidence that the estimator is correct.

### Validation on public datasets
We then ran the same engine, through the same API the Shiny module calls, on three public bulk RNA-seq datasets. They were chosen because they are standard reference datasets for differential expression methodology, not for any property of their results: `airway` (Himes et al. [16]; GSE52778; human airway smooth muscle, four donor cell lines each treated with dexamethasone or untreated, donor as covariate), `pasilla` (Brooks et al. [17]; GSE18508; *Drosophila* S2 cells, pasilla RNAi knockdown versus untreated, library type as covariate), and GSE60450 (Fu et al. [18]; mouse mammary gland, 2-day lactation versus 18.5-day pregnancy pooled over both cell populations, cell population as covariate), the last of these being the dataset of the limma/edgeR workflow of Law et al. [19]. A fourth run repeated the GSE60450 contrast within the basal population alone, which removes the covariate axis and reduces the design to two samples per group — the smallest the engine accepts — in order to see how the calibration behaves there. Every run used B = 20 bootstrap replicates, the default call rule (adjusted *p* ≤ 0.05, |log2FC| ≥ 1, direction consistency ≥ 0.90) and the 0.10 eFDR target, and is reproducible from `scripts/validate_airway.R`, `scripts/validate_pasilla.R` and `scripts/validate_gse60450.R`, with per-run outputs under `validation/results/`.

The eFDR curve was monotone non-increasing in τ in all four runs, as it was on synthetic data, taking between 5 and 11 distinct values. No specification was pruned, no model fit failed, and no gene was excluded for direction inconsistency in any run.

Two results qualify the procedure rather than support it. First, the curve already lay below the 0.10 target at the smallest attainable positive threshold in every run, so the automatic rule selected τ = 1/*m* every time — as it also did on the synthetic benchmark. Across five runs the selection rule has therefore never chosen anything other than the minimum, and on these datasets the stability threshold is not binding: the calibrated rule calls essentially every direction-consistent gene that reaches significance in at least one specification. Second, and as a consequence, the default single pipeline's DEG list was a strict *subset* of the multiverse calls in all four runs — not one gene was significant under the default DESeq2 analysis without also being called — while 72 to 398 genes were called by the multiverse without being significant under the default pipeline. The module's practical contribution on these data is therefore not a smaller, safer gene list; it is a stability annotation on a slightly larger one. A user who wants the threshold to do work must raise it manually, which the interface permits without refitting.

The stability annotation itself does separate genes sharply, and how sharply depends on whether a covariate axis is present. Of the default pipeline's DEGs, the fraction surviving *every* specification was 539 of 938 for airway and 163 of 224 for pasilla, but only 2 of 1,302 for GSE60450 with cell population as covariate, where the modal stability was exactly 0.5 (550 genes). Repeating that contrast within the basal population alone, which deletes the covariate axis, raised unanimity to 1,082 of 1,315. In this design the cell population is a very large effect, and whether it is adjusted for decides the fate of roughly half the gene list, whereas varying only the filter, the model family and shrinkage leaves most calls intact. That is exactly the kind of dependence the module exists to surface, and it is invisible in a single-pipeline report.

As a qualitative face-validity check we asked whether genes known from each original publication appear near the top of the stability ranking; this is not a quantitative recovery rate, since no ground truth exists here. For airway, seven of eight pre-specified glucocorticoid-response genes — CRISPLD2, DUSP1, KLF15, PER1, TSC22D3, FKBP5 and ZBTB16 — reached stability 1.000 at ranks 2 to 69. The eighth, CCL2, was not called: under the default pipeline it has log2FC −0.56 at adjusted *p* 0.033, so it is significant but fails the |log2FC| ≥ 1 call rule. For pasilla, *ps* itself, the RNAi target, reached stability 1.000 in the down direction at rank 62. For GSE60450, the milk-protein gene Csn1s2b reached stability 0.875 at rank 3, and Wap and Lalba were called at stability 0.500; in the basal-only run all three reached stability 1.000. Two pre-specified genes were not called: Csn2 (log2FC 0.88, adjusted *p* 0.68) and Mcl1 (log2FC −0.33, adjusted *p* 0.17), the latter being the focus of Fu et al. [18]. We report this plainly — at the gene level, in this contrast, Mcl1 is not differentially expressed under any specification, so this validation does not reproduce that paper's central claim and is not offered as doing so.

The runs surfaced, and led us to fix, one defect in the engine. `mv_fit_full_null()` was returning an undefined (`NA`) null mean and dispersion for any gene with zero counts in every sample; `mv_simulate_null()` propagated those `NA`s into the simulated count matrix, and the bootstrap then aborted. Real count matrices always contain such genes — 30,208 of 63,677 in airway — so the synthetic fixture, which has none, could not expose this; the validation scripts worked around it by dropping all-zero genes before calling the engine (30,208, 2,240, 6,414 and 7,155 removed in the four runs; no filter in the grid would have retained them). This is now fixed at the source: a gene with no observed counts has a well-defined null (it stays at zero), so `mv_fit_full_null()` sets its null mean to zero and its dispersion to a nominal floor instead of leaving either undefined, and a regression test with a synthetic all-zero gene now covers this case. Separately, the two-samples-per-group run completed without error but has only nine attainable stability values and five distinct eFDR values, and should be read as exploratory in line with the engine's own guidance on group size.

Wall-clock times were measured on an AMD Ryzen 5 7600X (6 cores, 12 threads) under WSL2 with R 4.5.2; the airway and GSE60450 runs were executed concurrently, so their times include contention and are upper bounds. At B = 20 a complete calibrated run on a real dataset took 8 to 27 minutes, which is consistent with the per-fit costs reported below and confirms that the batched asynchronous scheduler is necessary for interactive use.

### Computational cost
We measured single-fit cost on a simulated matrix of 20,000 genes × 12 samples: 4.35 s for one DESeq2 fit and 2.54 s for one edgeR quasi-likelihood fit. From these, the full 80-specification design at B = 100 is approximately 8,080 fits, or on the order of 5.6 CPU-hours, while the no-covariate 8-path grid used in the validation above, at B = 20, is approximately 168 fits, or on the order of 7 CPU-minutes (selecting a covariate column doubles the grid to 16 paths, approximately 14 CPU-minutes at B = 20). These figures are hardware- and data-dependent and are reported to make the cost structure explicit rather than as a benchmark of the software against alternatives: multiverse analysis with simulation-based calibration is inherently one to three orders of magnitude more expensive than a single pipeline, which is why the batched asynchronous scheduler and the no-refit re-thresholding design are load-bearing rather than cosmetic.

### Relation to existing tools
The multiverse module answers a different question from existing graphical RNA-seq platforms rather than competing with them on the same one. iDEP records and reproduces one selected workflow, including its parameters and generated code [2]; that is a solution to "can this analysis be repeated?". Multiverse DEG asks "how much does this conclusion depend on which defensible workflow was selected?", and returns a gene ranking under that criterion together with a calibrated error rate. The two are complementary, and the presence of code generation in iDEP is the reason we do not claim reproducible script generation as a contribution here.

The module is also distinct from the UpSet comparison already present in MultiverseDEG (step 8), which intersects DEG sets from *different biological contrasts*. Multiverse DEG fixes one contrast and varies only the analytic specification. The distinct `multiverse:` key prefix keeps the two from being confused if a multiverse result is later compared against biological contrasts in the same UpSet view.

### Interpretation
Three interpretive points are built into the module and should be stated explicitly. First, the specifications are not independent replications: they are re-analyses of the same samples, and a high stability value means the conclusion survives the declared choice set, not that it has been independently replicated. Second, the union of all specifications is not the discovery set; only genes passing the calibrated threshold and the direction-consistency requirement are called. Third, the reported quantity is an effective FDR, not a finite-sample FDR guarantee: fitted parameters are reused in the null construction, genes and specifications are correlated, and the calls are discrete, so we report eFDR with its bootstrap inputs and expected null discovery counts visible rather than asserting exact control. The in-application caption states the same point in plain language: more columns agreeing does not by itself make a gene reliable.

## Limitations and future directions
Validation rests on one synthetic benchmark and four runs over three public datasets. That is enough to show that the engine runs end to end on real count matrices, that the eFDR curve behaves as designed, and that the stability ranking places known biology at the top; it is not enough to characterise the procedure's error rate on real data, where no ground truth exists and the realised false discovery proportion cannot be measured at all. A larger evaluation — more datasets, more contrast types, and ideally spike-in or benchmark data with known truth — remains necessary before the eFDR is used as a quantitative error guarantee rather than a relative ranking aid. In particular, the automatic threshold selection rule chose the smallest attainable positive τ in every run performed so far, synthetic and real, so we have no evidence that it discriminates; on data with strong effects it does not, and users should treat τ as a parameter to set deliberately rather than one the software has solved. We also do not claim that the calibration transfers to data with unmeasured batch structure, zero inflation or outliers, none of which the public datasets used here stress.

The implemented grid is a reduced 8-path subset of the 80-specification full design. limma-voom, edgeR RLE and upper-quartile normalisation, DESeq2 LRT, ComBat-seq batch correction and IHW-based *p*-value weighting are deferred; ComBat-seq and IHW additionally require packages that were not available in the verified environment and will remain strictly optional. Permutation-based calibration is offered only as a sensitivity analysis and only where group sizes make the permutation distribution non-degenerate, since with three samples per group there are too few distinct unsigned partitions for a usable null.

The null model assumes a negative-binomial distribution and inherits whatever the DESeq2 fit did not capture. Designs in which batch and condition are perfectly confounded are rejected rather than analysed; strong unmeasured batch effects can misspecify the null, and runs with fewer than five samples per group are flagged as exploratory. Disk-backed resumption of interrupted runs and a proper result class replacing the current `padj`-compatibility hand-off are planned; the present hand-off reuses the `padj` field with an explicit result-type attribute, which is documented but is not a clean contract.

Finally, the application analyses bulk RNA-seq only, starting from a count matrix. Upstream processing from FASTQ and support for single-cell data are separate development tracks and are not part of v4.0.

## Conclusions
MultiverseDEG v4.0 provides count-matrix-to-figure bulk RNA-seq analysis in a locally deployable graphical interface, and adds a multiverse DEG module that makes the analytic choice set explicit instead of hiding it behind a default. By running the legal specifications for one contrast, ranking genes by direction-consistent stability, and calibrating that stability against a parametric negative-binomial null constructed from the full fitted model, the module reports which findings survive the analyst's discretion and at what estimated error rate. Its calibration has been demonstrated on a synthetic benchmark and exercised on three public datasets, where the eFDR curve behaved as designed and the stability ranking recovered known biology; what those runs also show is that on real data with strong effects the automatic threshold is not binding, so the stability ranking, rather than the threshold, carries the information.
